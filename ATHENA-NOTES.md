## 2026-11-03 — `/dataerasure`: request body no longer reaches the template engine when the Local File Read challenge is off

Looked at `routes/dataErasure.ts` (the POST handler), `views/dataErasureResult.hbs`, `lib/utils.ts` (`isChallengeEnabled` / safety mode), `data/static/challenges.yml` (`lfrChallenge` is `disabledEnv: Docker, Heroku`), `infrastructure/docker-compose.yml` (how this repository deploys itself) and `test/api/erasure-request.test.ts`. The recorded finding was hbs GHSA-7f5c-rpf4-86p8 (a request-controlled `layout` render option makes hbs read an arbitrary file into the response) reached through `res.render('dataErasureResult', { ...req.body, ... })`. Reading the handler showed the guard added in commit 5658473cf only wrapped the *challenge credit*: when the challenge is disabled (Docker, Heroku, `challenges.safetyMode: enabled`) the `else` branch still spread the whole request body into `res.render`, so a logged-in visitor could read any file in full, with neither the `ftp`/`ctf.key`/`encryptionkeys` denylist nor the 100-byte truncation the challenge branch applies. Ruled out a dependency bump (no hbs release fixes the advisory) and removing the challenge outright (it is an operator-gated training feature; the gate is the repository's own switch for it). Changed: the disabled path now renders with the theme variables only, and the challenge path passes only `layout` instead of the whole body. The result page never used anything from the body, so the page is unchanged for users. Added an API test that turns safety mode on, posts a file path as `layout`, and asserts the normal result page comes back rather than the file. The challenge itself still works where the operator has it enabled; set `challenges.safetyMode: enabled` to turn it off everywhere.
