# Athena notes

2026-11-03 — Fix for finding "hbs 4.2.0: arbitrary file read through user-controlled layout on /dataerasure". Looked at `routes/dataErasure.ts`, `views/dataErasureResult.hbs`, `lib/utils.ts` (challenge enablement), `data/static/challenges.yml` (lfrChallenge is disabled on Docker/Heroku) and the API and Cypress tests for `/dataerasure`. The POST handler spread the whole request body into `res.render('dataErasureResult', …)`; hbs (every released version, GHSA-7f5c-rpf4-86p8 / CVE-2021-32822) treats a `layout` render option as a file path and reads that file into the response. With the challenge enabled a substring denylist and a 100-byte truncation applied; with the challenge disabled (Docker, Heroku, safety mode) the fallback branch still spread the body, so `layout` reached hbs with no denylist and no truncation at all. The result view uses none of the posted fields, so the fix passes only the theme variables to `res.render` in both cases and drops the challenge-specific branch; the Local File Read challenge is therefore no longer solvable through this route (it remains listed). Updated the API tests that asserted the file read to assert the opposite, and the Cypress spec likewise. Ruled out upgrading hbs (no fixed release exists) and tightening the denylist (an allowlist of render options is the root-cause fix).
